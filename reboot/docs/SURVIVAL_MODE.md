# Endless survival — 2026-09-12

Evidence: owner requested an endless wave mode, playable solo and in two-player online co-op; every wave increases enemy count; occasional useful drops; avoid an overpowered immediate tank; a public survival-time leaderboard with one row per run and one/two separately entered player names. Names must not be able to break the service. Existing stack: TypeScript World, host-authoritative PeerJS snapshots, Cloudflare Pages advanced Worker with TURN/analytics bindings. No existing persistent score storage.

Implementation decisions (design assumptions): one compact vertical arena using existing pixel assets. 8-second preparation, 6-second intermissions; total wave size grows linearly without a fixed final wave. Spawn batches with an active population ceiling for frame time and readable combat. Escalate role mixes and vehicles; long waves add pressure rather than allowing an isolated enemy to end pressure forever. Active combat time is the score (pause, introductions and intermissions excluded). Solo death ends the run; in co-op, one downed player waits until the survivor clears the wave, both down ends it. Supplies drop periodically; no automatic ultimate refill. First tank after wave 5, subsequent opportunities every 5 waves, only one usable tank, less armor/firepower in survival only. Unlocked campaign progression stays untouched; all heroes available for this separate mode.

Public leaderboard: separate solo/duo views, shared team time and wave, each participant submits their own display name. Backend issues an opaque run/token pair for each slot; D1 stores one run row, makes it public only after finish and all names. Parameterized SQL, strict short name allowlist, bounded request bodies, finite integer stats, server elapsed-time plausibility, monotonic progress, idempotent completion, no client HTML rendering. This is a friendly prototype leaderboard: a browser host can still fabricate gameplay; this does not claim server-verified anti-cheat. Hosting continues on existing Cloudflare Pages, with one D1 database binding.

Sequence: simulation/arena → solo UI → host/guest synchronization → persistent API and leaderboard → integration and silent regression/browser verification → deploy. No campaign rewrites or new generated audio/art needed.

Implemented:
- `survival.ts` constructs a 44-tile vertical arena and runs the host-owned wave director. Wave budget `(6 + 3 × wave) × players`; simultaneous cap 16 solo / 22 duo, paced spawns, shuffled-by-cycle entry points at least 7 tiles from living players. Thirty seconds of sustained combat adds aerial reinforcements. HP multiplier caps at 1.8; the total wave budget has no final wave.
- Existing infantry roles, finite-range weapons, chase/navigation, shields, demolition, drones (wave 3), tanks (5), aircraft (7), SFX and dynamic music are reused. Arena radio is outside the approach corridor; central supply footing survives destruction. No new placeholder audio or artwork.
- Every fifth kill can drop a medkit, every seventh an ultimate crate, with bounded pickup arrays. Wave clear provides supplies and revives a downed partner with 65 HP and an empty ultimate. Reward tank on every fifth cleared wave only when no usable tank remains: 180 armor, 65 shell damage, 3.2 s reload. Campaign tank values unchanged.
- The guest receives the same survival state via protocol `uaforce-coop-7`; no guest wave simulation. Downed actors cannot move, attract attacks, block bullets, or drag the camera. Ending/leaving is a shared result; normal host tab close sends its final score with `sendBeacon`.
- Ukrainian and English menus, compact visible wave counter, solo/duo choice and public leaderboard. Survival sessions have distinct analytics modes. Campaign saves/unlocks are not written by survival.
- D1 `uaforce-survival` (`bb9933a1-be35-428d-bd3a-72e3d5c3c186`), production binding `SURVIVAL_DB`, created through in-app Cloudflare dashboard. Schema in `server/survival-schema.sql`. No tariff changes or paid add-ons enabled.
- API uses hashed opaque seat tokens, 2 KB streamed body limit, allowlisted 2–20 character names, prepared statements, same-origin JSON writes, best-effort per-isolate write throttling, server wall-time upper bound and monotonic/idempotent completion. Names render with `textContent`. QA runs are hidden from public rankings. Unpublished/QA rows expire after seven days, lazily on run creation.
- No promise of competitive anti-cheat: the browser host remains authoritative and can fabricate valid-looking stats. An abrupt browser/device crash can lose the final update; no host migration. If ranking service is unavailable, gameplay still runs, but the score may be unranked.
- Local development uses a Node SQLite D1 adapter and `.release/survival-dev.sqlite`; it never writes public rankings. `npm run dev -- --port 5179 --strictPort`, then `http://127.0.0.1:5179/?silent=1`. Node 25 used for development.
